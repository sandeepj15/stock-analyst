# Trading Research & Decision Engine

## Build Specification v1.0

**Working name:** SignalForge\
**Product type:** Research, analytics, backtesting, portfolio
intelligence and decision-support SaaS\
**Primary market:** Indian equities first; architecture must support
additional markets later\
**Primary user:** Retail investor/trader who wants a systematic research
workflow without needing institutional tools\
**Initial deployment:** Personal use + private beta\
**Primary stack:** Python, FastAPI, PostgreSQL, Redis, React/Next.js,
Docker, GitHub Actions\
**Optional:** Celery/Arq, DuckDB/Parquet, object storage,
Prometheus/Grafana

------------------------------------------------------------------------

# 1. Product Thesis

Build a research platform that turns raw market information into a
**transparent, reproducible, evidence-backed decision process**.

The product must NOT claim to predict prices with certainty.

It must answer:

1.  What is happening?
2.  What evidence supports that conclusion?
3.  What evidence contradicts it?
4.  How strong is the setup?
5.  What are the major risks?
6.  What has historically happened in similar setups?
7.  What is the risk/reward?
8.  How does the current market regime affect the setup?
9.  What changed since the user's last review?
10. Which assumptions or data are stale?

The system should be useful even if the user ignores every AI-generated
conclusion.

The deterministic analytics layer is the source of truth. AI is an
explanation, summarization and research-navigation layer.

# 2. Core Product Principles

## 2.1 Evidence before opinion

Every material conclusion must be traceable to:

`claim -> metric -> calculation -> source -> timestamp`

Example:

> "Price is above the 50 DMA."

Must resolve to:

-   symbol
-   calculation date/time
-   close price
-   50-DMA value
-   source dataset
-   source timestamp
-   calculation version

## 2.2 Deterministic analytics

Indicators, returns, drawdowns, ratios, scores, backtests and risk
metrics must be generated by deterministic code.

Do not ask an LLM to calculate RSI, CAGR, Sharpe, drawdown, position
size, etc.

## 2.3 AI cannot invent market facts

LLM prompts must receive structured facts and source references.

The LLM is not allowed to fabricate: - prices - financial ratios -
earnings - news - analyst estimates - dates - company facts - backtest
results

## 2.4 Every score must be decomposable

Never display:

`Score = 8.7/10`

without allowing:

`8.7 = Technical 8.9 + Momentum 8.2 + Fundamentals 7.8 + ...`

and showing the underlying evidence.

## 2.5 Historical performance is not future certainty

Backtests must clearly distinguish: - historical result - out-of-sample
result - hypothetical result - live/paper result

## 2.6 No look-ahead bias

Any feature used at timestamp T must only use information available at
or before T.

## 2.7 Survivorship-bias awareness

Historical universes must preserve delisted/dead securities where data
is available.

Do not backtest only today's surviving stocks and claim the result
represents the historical universe.

## 2.8 Corporate-action awareness

Prices and returns must distinguish: - raw OHLC - adjusted OHLC -
split-adjusted - dividend-adjusted - total-return series

The adjustment policy must be explicit.

# 7. Technology Decisions

## Backend

Python 3.12+

FastAPI

Pydantic v2

SQLAlchemy 2.x

Alembic

httpx

pandas

numpy

scipy where necessary

## Database

PostgreSQL

Use TimescaleDB if it materially simplifies time-series workloads.

Do not introduce TimescaleDB purely because the product contains
time-series data; ordinary PostgreSQL + partitioning can be sufficient
for MVP.

## Cache / queue

Redis

Background workers: - Celery, or - Arq

Choose one. Do not use both.

## Frontend

React + TypeScript.

Prefer Next.js if SEO/public stock pages are required.

Use a charting library capable of candlesticks and large time-series
datasets.

## Data science

pandas/numpy initially.

Move heavy historical calculations to: - Polars - DuckDB - Parquet

when profiling shows PostgreSQL/pandas is the bottleneck.

## Deployment

Docker everywhere.

Local: Docker Compose.

Production: AWS or GCP.

Suggested initial production:

``` text
Cloud Load Balancer
        |
      API
        |
  PostgreSQL
  Redis
  Worker
  Object Storage
```

Kubernetes should be optional rather than required for MVP.

# 8. Data Provider Strategy

This is a critical part of the project.

The data-provider abstraction must exist from day one.

Never hardcode the application to a single provider.

Create:

``` python
class MarketDataProvider(Protocol):
    get_instrument(...)
    get_daily_bars(...)
    get_intraday_bars(...)
    get_quotes(...)
```

Then implement provider adapters.

Potential data classes:

``` text
MarketDataProvider
FundamentalDataProvider
CorporateActionsProvider
NewsProvider
BenchmarkProvider
```

## Prototype

A development provider can use a suitable historical-data source.

However, do not assume a free source is suitable for a commercial SaaS.

Yahoo's developer/API terms impose restrictions that vary by API and
usage, and some services are not permitted for commercial SaaS use
without appropriate permission. Therefore the production architecture
must not depend on Yahoo data licensing assumptions.

## Production India data

Plan for licensed exchange/vendor data.

NSE currently offers multiple data products including real-time,
snapshot, delayed, historical and corporate data, and also has a
data-sharing/usage policy.

BSE similarly provides structured equity, derivatives, corporate and
delayed data products.

Before public commercialization: - verify redistribution/display
rights - verify storage rights - verify derived-data rights - verify API
limits - verify user-facing display permissions - verify commercial SaaS
rights

Never scrape an exchange website and silently turn that into a paid data
product.

# 11. Data Quality Layer

Every ingestion job must perform:

## Schema checks

-   required fields
-   numeric types
-   timestamp validity

## Range checks

``` text
high >= max(open, close)
low <= min(open, close)
volume >= 0
```

## Duplicate checks

No duplicate instrument/date/timeframe rows.

## Missing-data checks

Detect unexpected trading-day gaps.

## Corporate-action checks

Detect: - splits - bonuses - rights - dividends - symbol changes -
mergers

## Outlier checks

Flag extreme price changes rather than automatically deleting them.

A 40% move may be: - legitimate - split-related - bad data

Never silently normalize it.



# 27. Risk/Reward Engine

Inputs:

``` text
entry
stop
target
quantity
capital
```

Calculations:

``` text
risk_per_share = entry - stop
reward_per_share = target - entry

risk_reward =
reward_per_share / risk_per_share
```

Portfolio risk:

``` text
position_risk =
abs(entry - stop) * quantity
```

Risk percentage:

``` text
position_risk / portfolio_value
```

Allow user-defined maximum risk.

Example:

``` text
Portfolio = ₹5,00,000
Max trade risk = 1%

Maximum loss = ₹5,000
```

Position sizing:

``` text
quantity = floor(max_loss / risk_per_share)
```

Never hide the calculation.

# 30. Backtest Execution Rules

Use next-bar execution by default.

If a signal is generated from candle close at T:

``` text
signal at T
execution at T+1
```

Do not use the same candle's future high/low to simulate a perfect fill.

For stop/target logic where intrabar ordering is ambiguous:

-   use conservative assumptions
-   or require intraday data
-   or mark the trade as ambiguous

Never silently choose the favorable outcome.

deterministic tests.

# 102. The Most Important Engineering Rule

The product should be architected as:

``` text
                 RAW DATA
                    |
                    v
             DATA VALIDATION
                    |
                    v
              NORMALIZATION
                    |
                    v
             DETERMINISTIC
               ANALYTICS
                    |
                    v
                EVIDENCE
                    |
                    v
                SCORING
                    |
                    v
              EXPLANATION
                    |
                    v
              USER DECISION
```

Never:

``` text
RAW DATA
   |
   v
LLM
   |
   v
BUY
```

The first architecture can become a credible research platform.

The second is just another unreliable AI stock-tip application.

# 104. Final Product Definition

**SignalForge is an evidence-first market research and decision-support
platform for retail investors.**

Its core loop is:

``` text
COLLECT
   ↓
VALIDATE
   ↓
NORMALIZE
   ↓
ANALYZE
   ↓
SCORE
   ↓
EXPLAIN
   ↓
BACKTEST
   ↓
COMPARE
   ↓
MONITOR
   ↓
USER DECIDES
```

The strongest differentiator is not prediction.

It is **traceability**.

A user should be able to take any important statement on the platform
and ask:

> "Why does the system believe this?"

The answer must lead all the way back to data, calculation, methodology
and timestamp.
